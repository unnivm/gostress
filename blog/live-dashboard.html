Watch a Load Test as It Runs

November 7, 2026 5 min read GoStress Team

The GoStress dynamic dashboard turns a running test into a live view of request rate, latency, throughput, and failures—so you can spot changes before the run is over.

A final report is essential, but it arrives after the load test ends. During a long run, you may want to know whether throughput is still rising, when latency starts climbing, or whether errors began after a ramp-up step. GoStress can now show those signals while the test is in progress.

Start the live dashboard

Add --live-web to a normal stress test. The flag takes the address for the temporary dashboard server:

go run . \
  --url http://localhost:3000/api/orders \
  --c 100 \
  --d 60 \
  --ramp 20 \
  --live-web :8088

GoStress prints the dashboard URL when the server starts. Open it in a browser to follow the run. When the test completes, the page remains available with the finished snapshot until you stop the process.

What updates during the run?

The summary cards show requests per second, average data throughput, total requests, success rate, average and p99 latency, transport errors, and HTTP failures. The chart plots requests per second alongside average and p99 latency over time.

Because HTTP failures and transport errors are shown separately, a rising failure count has more context: the target may be returning unexpected status codes, or requests may be failing at the connection or transport layer. The dashboard also reports the test URL, method, elapsed time, concurrency, and ramp settings through its live data snapshot.

Use the timeline to investigate changes

The timeline is divided into one-second buckets. Compare its request-rate and latency lines around a point where behavior changes. For example, if latency climbs while request rate levels off, the target may have reached a capacity limit. If failures appear at the same time concurrency rises, inspect the server and its dependencies at that load level.

With --ramp, the live view is particularly useful: it lets you observe how the target responds as GoStress increases workers toward the configured concurrency. It gives you clues during the run; use the completed report and target-side telemetry to confirm the cause.

Designed to stay lightweight

The dashboard is served by the GoStress process and needs no separate monitoring stack or browser chart library. The page requests a JSON snapshot once per second. Latency percentiles are estimated from a fixed 64-bucket log-scale histogram, and the timeline uses a fixed-size ring buffer; the amount of retained monitoring data does not grow with the number of requests.

The displayed p50, p95, and p99 values are estimates from that histogram. Per-second chart p99 uses a capped sample of up to 1,000 successful latency measurements in each second. Treat these live values as operational signals; the final report is the place to review the completed run’s full calculated statistics.

Quick distinction: --live-web monitors a test as it runs. --serve-web opens the protected report dashboard for reviewing saved or imported report data. They serve different workflows.

A practical workflow

  1. Choose a representative endpoint and test duration.
  2. Start with a moderate concurrency, or add --ramp to increase load gradually.
  3. Open the printed live URL and watch throughput, latency, and failure trends together.
  4. After the run, compare what you observed with the generated report and the target system’s own metrics.

Live feedback makes it easier to catch a test that is going in an unexpected direction and gives you a timeline to investigate. To get started, see the GoStress usage guide or browse the other articles.
